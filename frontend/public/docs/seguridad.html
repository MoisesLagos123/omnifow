Seguridad y RBAC

Modelo de seguridad basado en perfiles configurables, permisos atómicos, JWT con rotación y audit log inmutable.

1. Modelo RBAC (Role-Based Access Control)

Principio fundamental: NO existen usuarios genéricos compartidos. Cada persona física que opera el sistema tiene su propia cuenta nominativa, con RUT y email únicos, asociada a uno o más Perfiles.

1.1 Conceptos

ConceptoDescripción
Usuario Persona física. Trazable e individual. Email + RUT únicos.
Perfil Agrupación de permisos que representa una responsabilidad organizacional. Configurable, no hardcoded.
Permiso Acción atómica sobre un recurso. Ej. venta.crear, precio.modificar.
Sucursal asignada Un usuario puede estar restringido a una o varias sucursales. Sin asignación, no opera en ninguna.

1.2 Cardinalidades

  • Usuario N—M Perfil (una persona puede tener varios perfiles, ej. "Vendedor" + "Cajero")
  • Perfil N—M Permiso (cada perfil tiene un conjunto de permisos atómicos)
  • Usuario N—M Sucursal (restricción explícita de dónde puede operar)

1.3 Perfiles sugeridos (configurables)

PerfilPermisos típicos
Vendedor / Cajero venta.crear · pago.registrar · stock.consultar · cliente.consultar · caja.operar
Reponedor inventario.ajustar · mercaderia.recepcionar · stock.consultar
Jefe de Sucursal Todo lo anterior + caja.cerrar · devolucion.autorizar · descuento.aprobar
Contador finanzas.ver · reportes.ver · cxc.gestionar · cxp.gestionar
Administrador precio.gestionar · producto.gestionar · proveedor.gestionar · reportes.ver
Sysadmin Inmutable TODOS los permisos del sistema. Perfil protegido: no se puede editar ni desactivar. Cualquier permiso nuevo se asigna automáticamente.

1.4 Verificación en defensa en profundidad

Cada Use Case verifica el permiso requerido independientemente de lo que muestre la UI. Aunque alguien encuentre cómo llegar a una pantalla sin pasar por el menú, el backend rechaza la operación. 

@requires_permission("venta.anular")
def execute(self, cmd: AnularVentaCommand) -> AnularVentaResult:
    ...

2. Autenticación: JWT con refresh

Esquema dual de tokens — access corto + refresh largo. La rotación detecta replay attacks y la revocación es inmediata server-side.

2.1 Características

  • Algoritmo RS256 (par de claves rotables). Firma asimétrica.
  • Access token TTL: 15 minutos. En header Authorization: Bearer.
  • Refresh token TTL: 7 días. Persistido en DB con jti.
  • Rotación: cada vez que se usa un refresh, se emite uno nuevo y se invalida el anterior.
  • Replay detection: si llega un refresh ya revocado → todos los tokens del usuario se invalidan (potencial robo).
  • Logout server-side: POST /auth/logout marca el refresh como revocado.
  • Cambio de contraseña: revoca TODOS los refresh tokens del usuario (forzar re-login en otros dispositivos).
  • Desactivación de usuario: revoca refresh tokens inmediatamente (sin esto un "usuario desactivado" podría operar 7 días).
  • Frontend tiene interceptor de 401 que refresca transparentemente y reintenta el request fallido (single-flight pattern).

2.2 Política de contraseñas

  • Argon2id para hashing (memory-hard, resistente a GPU/ASIC).
  • Mínimo 12 caracteres.
  • Validación contra lista de contraseñas comunes (HIBP / pwned).
  • Bloqueo temporal tras N intentos fallidos (rate limiting).
  • Anti shoulder-surfing en POS: campos password con autoComplete bloqueado y copy/paste/cut bloqueados (contextos multi-usuario en caja).

2.3 Reset por email

  • Usuario solicita reset con su email.
  • Backend genera PasswordResetToken de un solo uso, válido 1 hora.
  • Email enviado por SMTP (Resend o Gmail configurable).
  • Link al frontend con token en URL → pantalla de reset.
  • Al usar el token, se invalida + se hashea la nueva password.
  • Confirmación visual (no se filtra si el email existía o no — anti enumeración).

3. Audit Log inmutable

Bitácora completa de acciones sensibles. No se borra, no se edita. Retención mínima 1 año por exigencia financiera.

3.1 Qué se audita

  • Login (success / fail con razón)
  • Logout (server-side)
  • Cambio de password (sin guardar la password)
  • Reset de password (con email del solicitante)
  • Procesar venta (con folio, monto, cliente)
  • Anular venta / devolución (con motivo)
  • Cambios de precio (con valor anterior y nuevo)
  • Ajustes de inventario manual (con motivo)
  • Apertura / cierre de sesión de caja
  • Cambios RBAC: alta/baja de usuario, perfil, asignación de permisos
  • Cambios de configuración global

3.2 Datos persistidos por evento

CampoDescripción
usuario_idQuién hizo la acción
ipDirección IP (IPv4 o IPv6)
user_agentNavegador / cliente
accionCódigo del evento (ej. venta.procesar)
resultadoOK / FALLO
recurso_tipoTipo de entidad (Venta, Usuario, etc.)
recurso_idUUID del recurso afectado
beforeJSON del estado anterior (cuando aplica)

3.3 Visualización

Administración → Auditoría. Tabla filtrable por usuario, fecha, acción. Solo accesible con permiso audit.ver (típicamente Sysadmin / Contador).

4. Validación de entrada

Toda entrada se valida en la frontera (DTO Pydantic). Coerción explícita de tipos. Rechazo por defecto (allowlist sobre denylist).

4.1 Validaciones críticas

  • RUT — módulo 11 verificado (no aceptamos RUTs inválidos)
  • Email — formato + longitud máxima
  • Monto CLP — entero positivo, sin decimales
  • UUID — formato v7 verificado
  • Fecha — ISO 8601, UTC en DB
  • Cantidad — Decimal(14,3), no negativa
  • Idempotency-Key — header obligatorio en mutaciones críticas (POST venta, devolución, etc.)

4.2 Defensa OWASP

  • SQLi: queries parametrizadas (SQLAlchemy + driver psycopg). Nunca f-strings ni concatenación SQL.
  • XSS: React escapa por defecto. dangerouslySetInnerHTML está prohibido.
  • CSRF: cookies HttpOnly + SameSite=Strict para refresh.
  • IDOR: cada use case scope-ea queries por sucursales permitidas del contexto. Sin sucursal explícita y sin pertenecer a la del recurso → 403.
  • Mass assignment: DTOs Pydantic con campos explícitos. Nada de **body al constructor.

5. Transporte

  • HTTPS obligatorio en producción (HSTS habilitado).
  • Headers de seguridad: Content-Security-Policy, X-Content-Type-Options: nosniff, X-Frame-Options: DENY, Referrer-Policy: strict-origin-when-cross-origin.
  • CORS restrictivo: solo se permiten orígenes en allowlist (configurable por env).
  • Rate limiting por IP en endpoints sensibles: login, password reset.

6. Datos sensibles y secretos

  • .env en .gitignore. Plantilla .env.example sin valores reales.
  • Credenciales nunca en código ni en logs.
  • Hashes Argon2id de contraseñas. Texto plano nunca.
  • Tokens JWT firmados, no encriptados — no llevan datos sensibles. RUT, email, permisos en el payload.
  • RUT y datos PII guardados como están (Chile no requiere encriptación de RUT, pero sí integridad).
  • Backups automáticos cifrados (Neon Postgres encrypted at rest).

7. Sysadmin inmutable

El perfil Sysadmin tiene protecciones especiales para evitar lock-out accidental del sistema:

  • Marcado es_sistema=true en DB → no se puede editar nombre
  • No se puede desactivar
  • No se le pueden quitar permisos manualmente
  • Al sembrar nuevos permisos, Sysadmin los recibe automáticamente
  • UI: badge "Sistema" en su fila, botones de edición/desactivación deshabilitados
  • Excepción PerfilSistemaInmutableError en backend en 4 use cases (editar, desactivar, reactivar, asignar permisos)
Por qué importa: si alguien con intent maligno (o por error) desactiva el último Sysadmin, el sistema queda inoperable. Esta inmutabilidad es un guard-rail crítico.

8. Pruebas de seguridad

  • 616 tests backend: lógica de autorización en cada use case (acceso permitido vs. denegado).
  • 266 tests frontend: rutas protegidas con RequireAuth y RequirePermission.
  • Tests específicos de IDOR (acceso a recursos de otra sucursal → 403).
  • Pen-test interno antes de cada release mayor.
  • OWASP ASVS nivel 2 como referencia mínima.
  • Mypy strict en todo el backend (0 errores) → tipo-safety previene clase entera de bugs.
