Arquitectura, Patrones y Seguridad Mini ERP — POS multi-sucursal con módulo financiero · Chile / SII · CLP · v0 documental

1 Resumen ejecutivo

Sistema POS web con backend Python (FastAPI + SQLAlchemy + Postgres) y frontend React + TypeScript, diseñado bajo Clean Architecture con énfasis en:

Pilares

  • Atomicidad en operaciones financieras (Unit of Work).
  • Trazabilidad total — cada acción sensible queda en audit log con usuario nominativo.
  • RBAC por perfiles configurables, no usuarios genéricos.
  • Multi-sucursal desde el día 1.
  • Pagos mixtos (efectivo + tarjeta + transferencia en una sola venta).
  • Documentos tributarios Chile/SII con folios pesimistamente bloqueados.

Lo que NO entra en v0

  • Integración real con SII (firma + envío DTE) — solo emisión interna.
  • Modo offline en el POS — la app es web online.
  • Multi-moneda — solo CLP.
  • Multi-tenant (un solo emisor por instalación).

3 Clean Architecture · Capas

6.1 Repository

Interfaz genérica en el puerto. Implementaciones concretas en adapters/repositories/sql/ y adapters/repositories/memory/ (para tests).

# application/ports/repositories.py
from typing import Protocol, runtime_checkable
from uuid import UUID
from erp.domain.entities.venta import Venta

@runtime_checkable
class VentaRepository(Protocol):
    def guardar(self, venta: Venta) -> None: ...
    def obtener(self, id: UUID) -> Venta: ...
    def buscar_por_sucursal(self, sucursal_id: UUID, desde, hasta) -> list[Venta]: ...
Usamos Protocol (typing) en vez de ABC: duck typing estructural verificado por mypy --strict sin obligar a heredar.

6.2 Unit of Work

Envuelve una transacción. Use Case lo abre, ejecuta, y hace commit. Cualquier excepción → rollback automático.

# application/ports/unit_of_work.py
from typing import Protocol
from types import TracebackType

class UnitOfWork(Protocol):
    def __enter__(self) -> "UnitOfWork": ...
    def __exit__(
        self, exc_type: type[BaseException] | None,
        exc: BaseException | None, tb: TracebackType | None,
    ) -> None: ...
    def commit(self) -> None: ...
    def rollback(self) -> None: ...

# adapters/repositories/sql/sqlalchemy_uow.py
from sqlalchemy.orm import Session, sessionmaker

class SqlAlchemyUnitOfWork:
    def __init__(self, session_factory: sessionmaker):
        self._sf = session_factory
    def __enter__(self):
        self.session: Session = self._sf()
        return self
    def __exit__(self, exc_type, exc, tb):
        if exc_type is not None:
            self.session.rollback()
        self.session.close()
    def commit(self) -> None:
        self.session.commit()
    def rollback(self) -> None:
        self.session.rollback()

6.8 Decorator · @requires_permission

Cross-cutting. La autorización vive como decorador en la frontera del use case (defense in depth: igual se valida en la capa HTTP).

# adapters/security/rbac_decorator.py
from functools import wraps
from erp.domain.exceptions import PermisoDenegadoError

def requires_permission(permiso: str):
    def deco(fn):
        @wraps(fn)
        def wrapper(self, cmd, *, contexto, **kw):
            if permiso not in contexto.permisos:
                raise PermisoDenegadoError(
                    code="ERR_PERMISO_DENEGADO",
                    message=f"Falta permiso: {permiso}",
                )
            return fn(self, cmd, contexto=contexto, **kw)
        return wrapper
    return deco

class ProcesarVentaUseCase:
    @requires_permission("venta.crear")
    def execute(self, cmd, *, contexto): ...

6.9 CQS — separar lecturas de escrituras

Los writes pasan por Use Cases con UoW completo. Los reads simples pueden ir directo a un read model (ReadRepository) sin abrir UoW. Reportes complejos pueden usar SQL nativo optimizado, fuera del modelo de dominio.

No es CQRS completo (no hay buses ni proyecciones separadas). Es CQS pragmático: simplifica reads sin penalizar consistencia de writes.

7.3 Dominio · Inventario

El stock se mantiene como una tabla agregada STOCK por (producto, bodega) con campo version para optimistic-locking opcional. Toda variación queda registrada en MOV_INVENTARIO referenciando la causa (venta, compra, devolución, ajuste, transferencia).

Decisión · Costo promedio por bodega. El campo costo_promedio_clp vive en STOCK, no en PRODUCTO: cada bodega puede recibir el mismo producto a precios distintos (compras separadas, traslados con costos diferentes), por lo que el promedio se mantiene independiente por (producto, bodega). Para reportes consolidados a nivel producto, se calcula promedio ponderado on-the-fly: SUM(stock.cantidad × stock.costo_promedio) / SUM(stock.cantidad).
Decisión · Transferencias entre bodegas. Una transferencia genera dos filas en MOV_INVENTARIO (una SALIDA en bodega origen, una ENTRADA en bodega destino) ligadas por un transferencia_id común (UUID v7). Esto preserva la simetría con los demás tipos de movimiento (cada fila = un evento atómico sobre una bodega) y permite reconstruir la transferencia haciendo WHERE transferencia_id = ?. El costo promedio del destino se recalcula al ingresar.

Decisión · Control de vencimiento por lotes (opt-in). Cuando PRODUCTO.controla_vencimiento = true, cada ingreso crea/actualiza un LOTE_INVENTARIO con sus fechas. El STOCK agregado se mantiene como caché/total para valorización; los lotes aportan el detalle de vencimiento. Invariante: para perecibles, SUM(lote.cantidad WHERE NOT agotado) == stock.cantidad. El egreso usa FEFO (First Expired First Out): descuenta del lote que vence primero, registrando mov_inventario.lote_id. Productos sin control de vencimiento ignoran por completo la tabla de lotes.

Recálculo de costo promedio (al recibir cantidad q a costo c)

stock_nuevo.cantidad        = stock.cantidad + q
stock_nuevo.costo_promedio  = (stock.cantidad * stock.costo_promedio + q * c)
                              / (stock.cantidad + q)

Aplica a entradas por compra, transferencia recibida y devolución de cliente. Las salidas no alteran el costo promedio (solo descuentan cantidad al promedio vigente).

7.9 Reglas de integridad transversales

  • Soft delete para entidades maestras (activo BOOLEAN): nunca se borran usuarios, productos, clientes ni proveedores. Solo se marcan inactivos.
  • Hard delete permitido solo en tablas pivote y datos transitorios (idempotency_keys, intentos_login antiguos).
  • Snapshot de precios y costos: detalle_venta y detalle_compra guardan precio/costo al momento de la transacción (no se calcula on-the-fly desde producto).
  • Montos en CLP enteros (BIGINT) en todas las tablas — sin decimales en presentación. Decimal solo para cantidades de producto (NUMERIC(14,3)).
  • Timestamps en UTC (TIMESTAMPTZ). Conversión a America/Santiago solo en presentación.
  • UUIDs v7 generados por la aplicación, no por la DB.
  • FK con ON DELETE:
    • CASCADE en pivotes (usuario_perfil, perfil_permiso, detalle_venta, detalle_compra, pago).
    • RESTRICT (default) en referencias entre maestros y transacciones — proteger histórico.

10 Idempotencia

Mutables críticos exigen header Idempotency-Key. El middleware:

  1. Lee el header (si falta en endpoint que lo requiere → 400 ERR_IDEMPOTENCY_REQUIRED).
  2. Calcula SHA-256(body).
  3. Busca (key, endpoint) en idempotency_keys.
    • Existe + mismo hash → devuelve respuesta previa.
    • Existe + hash distinto → 409 ERR_IDEMPOTENCY_CONFLICT.
    • No existe → procesa, persiste resultado al final.

11 Modelo de Seguridad

Autenticación

  • Argon2id, parámetros: t=3, m=64MB, p=1.
  • JWT RS256, par de claves rotables (kid).
  • Access 15 min · Refresh 7 días.
  • Refresh persistido (jti, ip, ua), revocable.
  • Rotación de refresh: cada uso emite nuevo y revoca anterior.

Autorización (RBAC)

  • Usuario → N Perfiles → N Permisos.
  • Restricción adicional por sucursal.
  • Verificación en Use Case (decorador) y en HTTP (guard).
  • Mínimo privilegio.

Datos

  • TLS en transporte. Cifrado en reposo (Postgres TDE/disco).
  • Secretos via env / secret manager.
  • Backups cifrados.

Auditoría

  • Audit log inmutable, append-only.
  • Acción + actor + recurso + before/after + ts UTC.
  • Retención mínima 1 año.

Reglas

  • Mensaje de error genérico: ERR_AUTH_INVALIDA "Credenciales inválidas" (no revelar si el email existe).
  • Tras 5 fallos consecutivos: bloqueo por 15 min con backoff exponencial al siguiente bloque.
  • Rate limit a nivel HTTP: 5 req/min por IP, 10 req/min por email.
  • Auditar tanto éxito como fracaso.

11.2 UC Seguridad · Refresh Token

ActorUsuario autenticado PrecondiciónRefresh token válido y no revocado PostcondiciónNuevo access + nuevo refresh; refresh anterior revocado
  1. Cliente envía POST /api/v1/auth/refresh con cookie HttpOnly.
  2. Validar firma y expiración del refresh.
  3. Buscar refresh_tokens por jti; si revocado_en ≠ null → 401 ERR_REFRESH_REVOCADO.
  4. Marcar revocado_en = NOW(), emitir nuevo par, insertar nuevo refresh.
  5. Si la misma jti intenta usarse otra vez → revocar TODOS los refresh del usuario (sospecha de robo).

13 Observabilidad

  • Logs JSON estructurado con request_id, usuario_id, endpoint, latencia, error.code si aplica. Sin secretos ni PII completa.
  • Métricas (Prometheus): RPS por endpoint, latencias p50/p95/p99, errores 4xx/5xx por code, locks en stock/folios, sesiones abiertas, ventas/min por sucursal.
  • Traces (OpenTelemetry): span por request, sub-spans por use case, repo call, DB query.
  • Healthchecks: /health (liveness, retorna 200 si proceso vivo), /ready (readiness, valida DB).
