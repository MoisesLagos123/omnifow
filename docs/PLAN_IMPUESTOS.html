Rediseño Tributario

Plan completo para migrar el cálculo de IVA, ILA e IABA desde el modelo plano actual a un sistema basado en categorías, subcategorías y regímenes tributarios. Diseñado para Chile (Ley 825) y preparado para evolucionar.

1. El problema actual

Hoy el sistema guarda un campo iva_porcentaje en cada Producto (default 19) y lo copia al DetalleVenta al confirmar la venta. Esto genera 4 problemas críticos:

Problema 1 Redundancia masiva

Si tienes 500 productos, hay 500 filas con el valor "19" repetido. Si el SII sube el IVA al 22%, hay que actualizar 500 filas (o ejecutar un UPDATE masivo). Si te olvidas un producto, ese producto sigue cobrando IVA equivocado por meses.

Problema 2 No soporta impuestos adicionales

Un vino tinto en Chile no paga solo IVA 19% — paga ILA 20.5% + IVA 19%. Una Coca-Cola paga IABA 18% + IVA 19%. El modelo actual no tiene forma de representar esto. Si vendes alcohol o bebidas azucaradas, el sistema te calcula impuestos incorrectos. Eso es ilegal frente al SII.

Problema 3 Granularidad equivocada

El IVA NO es una propiedad del producto. Es una propiedad del sistema fiscal del país. Asignar el IVA por producto es como asignar la zona horaria a cada timestamp por separado.

Problema 4 Imposible reportar al SII

El SII exige reportar IVA débito fiscal por separado del ILA o IABA. Si solo guardas un iva_clp mezclado, no puedes desglosar el ILA de las ventas de vino cuando llega la auditoría. Hay que reconstruir manualmente.

2. Cómo es la realidad en Chile

Chile (DL 825) aplica tres tipos principales de impuestos al consumo, a veces en cascada:

2.1 Tasas vigentes (2026)

Categoría de producto Impuesto adicional + IVA Total efectivo*
Estándar (alimentos, snacks, limpieza, ropa) — 19% 19%
Vinos, cervezas, sidra ILA 20.5% 19% 43.4%
Licores ≥15° GL (pisco, whisky, ron) ILA 31.5% 19% 56.5%
Bebidas analcohólicas >15g azúcar/100ml IABA 18% 19% 40.4%
Bebidas analcohólicas ≤15g azúcar/100ml IABA 10% 19% 30.9%
Aguas minerales / saborizadas IABA 10% 19% 30.9%
Libros, servicios médicos, educación — Exento 0%

* Calculado sobre el precio NETO. El total efectivo no es la suma de las dos tasas porque el IVA se aplica sobre la base CON el recargo adicional incluido.

2.2 Fórmula de cálculo en cascada

Regla universal de impuestos chilenos:

precio_total = neto + impuesto_adicional + IVA(neto + impuesto_adicional)

donde:
  impuesto_adicional = neto × tasa_adicional   (ILA o IABA, si aplica)
  IVA                = (neto + impuesto_adicional) × 0.19

2.3 Por qué los impuestos adicionales no son IVA

ILA e IABA son impuestos al consumo específicos distintos del IVA. Se declaran en formularios separados al SII (F-29 mensual), tienen ventajas de retención propias y se contabilizan por separado. Por eso el sistema debe guardarlos como impuestos individuales en el snapshot de cada venta, no mezclarlos en un solo campo iva_clp.

4. Modelo de datos propuesto

4.1 Estrategia: categorías + subcategorías + regímenes

Tres niveles de configuración con responsabilidades claras:

  • Categoría agrupa visualmente (operativa, navegación en POS). NO tiene régimen.
  • Subcategoría es la unidad tributaria. Pertenece a UNA categoría. SIEMPRE tiene régimen.
  • Producto pertenece a UNA subcategoría. Puede tener override opcional (caso excepcional).

4.3 Resolución del régimen efectivo

Al procesar una venta, el sistema resuelve el régimen así:

def regimen_efectivo(producto):
    # 1. ¿El producto tiene override explícito?
    if producto.regimen_tributario_id is not None:
        return producto.regimen_tributario
    # 2. Si no, hereda de su subcategoría (que siempre tiene régimen)
    return producto.subcategoria.regimen_tributario

7. Plan de implementación

Implementación dividida en 6 fases. Cada fase es independiente, mergeable y reversible. Total estimado: 6-8 días reales.

1

Dominio + cálculo (sin tocar DB) Día 1

  • Entidades de dominio: TipoImpuesto, RegimenTributario, Categoria, Subcategoria
  • Service CalculoImpuestos.aplicar(regimen, neto) con tests exhaustivos (los 5 casos de uso + edge cases: exento, sin recargo, recargo + IVA)
  • Snapshot helper impuestos_aplicados_a_json(...)

Entregable: tests de dominio en verde con cálculos correctos para vino, cerveza, Coca-Cola, libro, detergente.

2

Modelo ORM + migración Alembic Día 2

  • Tablas nuevas: tipo_impuesto, regimen_tributario, regimen_tipo_impuesto, subcategoria, configuracion_finanzas
  • Migración Alembic: agregar columnas a producto, detalle_venta, categoria
  • Data migration: convertir producto.iva_porcentaje existente a régimen apropiado
  • Seed: tipos de impuesto + 6 regímenes base (ESTANDAR, EXENTO, VINO_CERVEZA, etc.)

Entregable: migración corre limpia, base de datos tiene seed completo, tests de integración con DB real pasan.

3

Use cases nuevos Día 3-4

  • CRUD de Tipos de impuesto, Regímenes, Subcategorías (admin only)
  • CambiarTasaTipoImpuestoUseCase — con audit log
  • AsignarRegimenSubcategoriaUseCase
  • Refactor ProcesarVentaUseCase para usar el nuevo cálculo
  • Refactor EmitirGuiaDespachoUseCase
  • Eliminar usos de producto.iva_porcentaje (deprecar)

Entregable: backend ya calcula impuestos correctamente. Toda venta nueva tiene snapshot correcto.

4

Frontend: pantalla Tributación Día 5

  • Nueva ruta /admin/tributacion (rol Sysadmin / Contador)
  • Tab "Tipos de impuesto" con tabla editable
  • Tab "Regímenes" con tabla editable + asignación M:N de impuestos
  • Modal "Crear / editar régimen" con preview de cálculo (caja para probar)
  • Audit log embebido (quién cambió qué)
5

Frontend: Categorías + Subcategorías + Producto Día 6

  • Pantalla Categorías: agregar columna "# Subcategorías"
  • Nueva subpantalla "Subcategorías" dentro de Categoría: tabla con régimen
  • En Producto edit: input "Categoría" → dropdown dependiente "Subcategoría" → preview régimen efectivo
  • Opción "Override de régimen" (collapsed por default, con campo motivo obligatorio)
  • En carrito POS: cada línea muestra desglose neto · ILA · IVA = total
  • En boleta impresa: desglose claro de cada impuesto

8. Riesgos y mitigaciones

Riesgo 1 Migración rompe ventas históricas

Mitigación: el snapshot impuestos_aplicados es nuevo y se llena solo para ventas futuras. Las viejas siguen mostrando iva_clp tal cual están. NO se recalculan. Los reportes históricos consultan el formato viejo, los nuevos consultan el snapshot.

Riesgo 2 Operador asigna régimen incorrecto

Mitigación: el sistema NO puede validar automáticamente si una Coca-Cola está en régimen LICOR_FUERTE. Pero sí podemos: (1) pedir motivo obligatorio en override de producto, (2) tabla "Productos con override" para revisión periódica, (3) audit log de todos los cambios de régimen.

Riesgo 3 Cambio de tasa afecta ventas en curso

Mitigación: al editar la tasa de un tipo_impuesto, confirmar con modal "Esto afectará todas las ventas a partir de AHORA". Recomendar usar vigente_desde futura para programar el cambio.

Riesgo 4 Subcategoría queda sin régimen

Mitigación: regimen_tributario_id NOT NULL en el schema de subcategoria (constraint a nivel DB). Crear subcategoría sin régimen es imposible.

Riesgo 5 Productos huérfanos al desactivar subcategoría

Mitigación: al desactivar subcategoría, sistema busca productos vivos asignados a ella y bloquea la operación. Si el admin confirma, los marca como "necesitan reasignación" en una vista de mantenimiento. Hard delete prohibido por integridad referencial.

Decisión ¿Procedemos?

Si confirmas este plan, empiezo por la Fase 1 (dominio + tests) y avanzamos secuencial con PRs revisables en cada fase. Cada fase es reversible — si surge un blocker, podemos pausar sin que el sistema quede inconsistente.
